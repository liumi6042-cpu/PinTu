# 本周榜、个人纪录与本地服务器保障

## 玩家可见变化

- 用时榜增加本周/历史切换；本周从北京时间周一 00:00 开始，以完成时间归档。网址保留筛选条件，回到页面时可继续查看。
- 在相同图片、片数、模式和累计参与人数条件下，显示个人最佳及实际名次，即使没有进入前 50 名也能查看。参与过的成绩会标注“有你参与”。
- 个人纪录按服务器验证的账号与当前浏览器游客身份查询；不会按昵称认领成绩，也不会把本机存档上传冒充用时成绩。仍保留旧公开成绩，只从尚存的已完成房间回填可证明的身份。
- 完成拼图后由服务器确认首次纪录、严格更快的个人最佳或追平纪录。合作成绩归参与过操作的玩家，围观者不会收到个人纪录提示。
- 说明“最多 8 人同时在线”和“整局累计实际操作人数”的区别。多人轮换后累计人数可以超过 8 人。

## 本地服务

启动方式和对外地址不变：`启动本地拼图.cmd`，本机 `http://localhost:3000`，局域网地址由启动器显示。

3000 端口现在由本地请求入口提供服务，游戏运行器仅监听 `127.0.0.1:3002`。入口保留 Host/Origin、登录 Cookie 与流式资源传输；按真实连接地址、接口类型和凭证摘要限流。频繁请求返回 429 与 Retry-After。正常拖动、轮询和鼠标有各自预算，同一 Wi-Fi 下的正常玩家不会共用一个很小的操作额度。来源 IP 不采信客户端提供的转发头。身份数量、并发连接、请求体和指标样本均有上限。

房间只读缓存最多 8 间、序列化文本计 2 MiB。每次请求仍在 SQLite 校验版本与到期时间；命中后不再反复传输和解析完整房间 JSON。只读对象深度冻结，修改必须复制，原来的版本条件写入和成员鉴权保留。

这些保护属于当前本地启动程序，尚未部署公网；不能据此声称公网入口已有相同保护或验证了公网容量。

## 查看运行状态

双击根目录的 `查看服务器状态.cmd`，可查看请求量、最近一分钟 P95 延迟、服务器错误、限流次数，以及入口和游戏运行器进程树各自的内存。

- 状态每 15 秒更新到 `work/local-server/status.json`。
- 汇总日志每分钟写入 `work/local-server/metrics.jsonl`，约 5 MiB 轮转一次，最多 3 个文件。
- 记录接口类型和统计数字，不记录 Cookie、令牌、昵称、房间编号、完整网址查询参数或请求内容。
- 内存来自 Windows 进程树采样，包含本地 Wrangler/模拟运行器；不是浏览器帧率，也不等同于正式部署实例的内存。
- 请求统计在启动时重置，历史汇总日志保留。

## 备份与恢复

每次启动迁移前备份；服务运行期间每小时检查一次，距最近有效自动备份满 24 小时再生成备份。自动备份保留最近 7 份，手动备份不自动删除。只有本工具识别且校验成功的旧自动备份会参与清理。

双击 `立即备份数据库.cmd` 可随时手动备份。使用 SQLite 在线备份 API，包含已提交的 WAL 内容，每份备份都有真实文件大小、SHA-256 和数据库完整性检查。工具依据：[Node SQLite backup](https://nodejs.org/api/sqlite.html#sqlitebackupsourcedb-path-options)、[SQLite 在线备份](https://www.sqlite.org/backup.html)。

备份保存在 `work/backups/automatic`、`manual`；不通过网页暴露。这里备份服务器数据库，不包括浏览器里的本机单人存档，也不重复备份项目内的图片原件。当前备份仍在同一台电脑上，不能抵御整块磁盘损坏；需要保留到其他磁盘时，可以复制已完成的备份目录。

恢复步骤：

1. 停止本地服务器，确认 3000 和 3002 端口已释放。
2. 在项目目录运行 `scripts/maintenance.ps1 verify -Snapshot "备份目录的完整路径"`。
3. 确认需要回到该时间点后运行 `scripts/maintenance.ps1 restore -Snapshot "备份目录的完整路径" -ConfirmRestore`。
4. 重新运行 `启动本地拼图.cmd`。

恢复会把服务器数据回退到选定备份。工具会先验证全部文件，并自动把当前数据库保存到 `work/backups/before-restore`，然后暂存、验证和替换恢复文件。运行中的服务器、无效路径、被修改的备份会被拒绝。恢复功能已在隔离测试库验证，没有对用户现有数据库执行回退。

## 验证与实测

- TypeScript 和本地生产构建通过。40 项相关单元/回归检查通过，包含周一/跨年边界、纪录比较、冻结缓存隔离及容量、WAL 备份、校验失败拒绝、恢复保留救援副本、自动清理边界、限流、原多人同步与双语行为。
- 4 项真实 HTTP 回归串行通过：局域网及同源校验、会员名额和到期规则、榜单与真实最后一片落块的个人纪录、RoomClient 拖动与重连。个人最佳第 57 名也可显示，匿名和同名其他玩家不能认领。SQL 身份查询使用 owner 索引。
- 数据库写入夹具需串行运行；首次同时启动夹具时外部 SQLite 写入争用导致一次 SQLITE_BUSY，改为 `--test-concurrency=1` 后上述回归全部通过。
- 单独进行了两次同场景压力测试：先 1 桌 8 人运行 8 秒，再 3 桌 24 人运行 24 秒；每桌 2000 片，所有玩家同步鼠标和轮询，每桌 1 人持续拖动。

| 场景 | 优化前 P95 | 缓存优化后 P95 | 优化后拖动请求 P95 |
|---|---:|---:|---:|
| 1 桌 / 8 人 | 359 ms | 377 ms | 305 ms |
| 3 桌 / 24 人 | 1318 ms | 1124 ms | 1101 ms |

优化后的测试共 2168 次请求，失败 0 次，所有房间最终拼块状态一致。24 人阶段采样的本地运行器进程树内存约 998 MiB，入口约 72 MiB；这些是有限采样，不是峰值上限。多房间场景仍有约一秒级同步延迟，扩大规模前还需继续优化和更长时间测试，不能把本次短测当作容量保证。

实测报告保存在 `work/load-tests/before-room-cache.json` 和 `work/load-tests/latest.json`。测试房间、账号和成绩均按本次独立 ID 清理；用户进度、既有成绩、图库和会员规则保留。未执行浏览器 DOM、截图或模拟点按验收，未发布公网；本地服务保持运行。

```powershell
$env:PUZZLE_TEST_LOAD='1'
node --import ./tests/ts-register.mjs --test tests/multi-room-load.test.mjs
```

限流预算参考了按接口/身份/来源分层限制的原则：[OWASP 防自动化指南](https://cheatsheetseries.owasp.org/cheatsheets/Bot_Management_and_Anti-Automation_Cheat_Sheet.html)。当前数值面向本地试玩，需要随运行数据调整。
