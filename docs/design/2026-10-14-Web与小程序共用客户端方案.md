# Web 与小程序共用客户端方案

日期：2026-10-14  
状态：第一步已完成，可在 http://127.0.0.1:3223/ 试玩；账号迁移与线上入口切换在试玩确认后继续。

## 建议

以当前小程序使用的共享游戏客户端为主，增加正式的普通 Web 入口。相册、每日图片、任务、成长、金币、装饰、拼图和社交功能共用实现，按屏幕和输入方式调整布局。停止在原 Web 前端逐项重做这些功能。

后续新游戏逐步使用同一套游戏服务；原 Web 登录、旧房间及历史权益通过兼容层保留。统一程序不等于自动统一账号与存档，二者分阶段验收。

沿用此前约定：Web 不使用体力，其他奖励与小程序共用后台配置。

## 为什么可行

当前小程序并非只能在微信运行的页面。`mobile/` 是共享 Canvas 游戏客户端，已有微信入口与浏览器入口，两者共用界面、游戏逻辑和网络客户端。构建脚本已能生成微信包和浏览器包。

现有浏览器包主要面向 TapTap，尚不能直接替换普通 Web 网站：平台名称与配置、身份、体力规则、广告入口和桌面操作均需适配。这项工作属于扩展已有共享客户端，无需复制第三套相册、任务或装饰页面。

## 共用范围与平台差异

| 内容 | 建议处理 |
| --- | --- |
| 相册、每日图片、任务、成长、金币、装饰、收集 | 共用界面逻辑、规则与管理后台；新功能在共享客户端实现一次 |
| 相册显隐 | 保留后台“PC 显示 / 小程序显示”；没有可展示图片时自动隐藏 |
| 任务奖励 | 继续共用一份配置，Web 发放金币、经验等适用奖励；仅体力的入口不在 Web 展示 |
| 体力 | Web 的服务器规则同时跳过扣除和体力不足限制，界面隐藏相关数值与文案 |
| 登录 | 浏览器沿用原 Web 登录入口，接入统一游戏身份；微信侧保留平台适配 |
| 分享、文件选择、全屏等 | 使用各平台能力，游戏业务共用 |
| 广告 | 普通浏览器当前没有可直接使用的激励广告能力；先检查提示、底图、建房券等依赖，给出可用入口和明确规则，不保留无法完成的广告按钮，也不擅自免费发放广告奖励 |

服务器根据可信入口和会话区分平台，包括相册显示与是否消耗体力。当前相册平台筛选是服务进程级配置，合并服务时需调整，不能只让浏览器自报平台。

## 界面方案：同一套页面，三种布局

按可用宽高和输入设备选择手机竖屏、手机横屏、电脑宽屏布局；避免把手机界面等比例拉宽。

| 页面 | 电脑宽屏 | 手机横屏 |
| --- | --- | --- |
| 大厅与相册 | 固定导航、清晰的相册列表、多列图片；详情在侧面或适宽弹窗中展示 | 缩短顶栏，增加图片列数，减少上下占用 |
| 任务、成长与装饰 | 任务与礼包在左下角窄浮窗中显示，统一奖励展示；成长与装饰保持适宽页面 | 任务浮窗按可用高度滚动，窗外仍可移动画面与拼块 |
| 拼图 | 共用手机版的全宽桌面、收起式工具及按需查看原图；聊天与托盘可收起 | 精简顶部信息，侧面展开工具，优先保证操作空间 |

继承现有虚线网格、协作光标、参考图、整理和拼块拖动。电脑补齐鼠标所在位置缩放、滚轮/触控板、空格或中键平移、Esc 关闭弹窗、列表滚轮及鼠标反馈。

现有代码已包含部分横屏分支，但任务、图鉴切换、通用弹窗和工具入口仍明显偏手机。微信构建目前固定竖屏；Web 宽屏适配与微信客户端是否开放横屏应分别验收，不能以浏览器横屏可用代替微信真机验收。

## 原 Web 功能与玩家数据

### 保留原账号与资产

原 Web 与移动游戏服务当前使用不同身份和数据结构，直接切换到现有浏览器包会进入移动端游客体系。

保留原 Web 登录，由服务器验证后交换游戏会话，为账号和原游客建立稳定映射。迁移金币、等级、装饰、已购相册及图片、任务礼包和领取记录时，记录来源并保证重复执行不会重复发放。不得按昵称合并玩家，不得以新默认值覆盖旧资产。

目标可以是一套游戏服务，但跨端同一账号、同一背包需要另加明确的绑定流程。首轮范围优先保证原 Web 用户继续使用自己的资产；不强迫用户先绑定微信。

### 保留旧房间

新建游戏转入统一服务；旧房间链接继续进入兼容入口，保持拼块位置、参与者和进度。若旧房间完成后仍有奖励，通过可去重的结算接入唯一钱包，避免新旧服务分别发奖。

### 防止替换后功能缩水

原 Web 支持 1000 片，当前移动版创建档位最高 500 片；原 Web 还有自定义图片及旧单人/私密房间。将这些列入替换前清单：1000 片与上传图片优先补为共享客户端的桌面能力，旧局先保留兼容入口。若要取消某项功能，应明确列出再决定。

新建房间规则以小程序为主，但原 Web 已有的购买、会员或其他授权继续保留；不能因为更换客户端而失效。

## 实施顺序

### 第一步：交付可试玩的宽屏预览

增加普通 Web 构建入口，使用隔离体验数据，完成大厅、相册、任务和拼图的桌面布局与输入。展示电脑宽屏和手机横屏两种体验，让用户先判断是否采用。线上入口和玩家数据保持原状。

这一阶段同时列清体力、广告、建房、上传图片与大片数差异，避免在视觉确认后才发现关键功能无法衔接。

### 第二步：接通账号、资产与游戏服务

实现 Web 登录交换、平台规则、资产迁移及旧房兼容；新功能只接入共享服务。后台继续使用现有保存内容和四份公开配置，不重建或恢复旧基线。

重点验证登录续用、已购权益、奖励不重复、旧房续玩、Web 不受体力限制、两端相册显隐以及每日图片。只针对变更和玩家数据做必要验证，不做无关的全量重复测试。

### 第三步：确认后切换网站入口

新局统一进入共享客户端；旧房保持兼容访问。保留可恢复的旧入口和发布版本，出现问题可切回。网站介绍、帮助、旧图片或相册链接按需保留轻量页面或合理跳转，不再为 SEO 维护第二套游戏界面。

客户端上线与后台内容发布分别处理；上线不能擅自发布管理员尚未确认的内容。

## 工作量判断

一次性的主要工作是桌面交互、平台规则和旧用户兼容，不是重新开发相册、任务、金币与装饰。完成后，大多数功能与修复可以共用，长期维护成本会低于持续向旧 Web 搬运小程序功能。

建议先批准第一步，以实际宽屏试玩结果决定是否进入迁移与切换。当前不承诺“只改横屏样式即可直接上线”。
