# 图片库来源与扩充规范

用户已确定：后续拼图内容均由我们为本项目生成；不使用未确认可商用的网络素材。生成、筛选和扩充均沿用这个方向。

## 第二种来源：用户提供并授权的图片（2026-09-17 新增）

用户 2026-09-17 决定：**用户自己提供、并明确授权本站使用的图片，可以直接进图库上架**，不再要求它有 AI 生成记录和提示词。

理由是原来的要求属来源错配：「生成工具、提示词、参考图哈希链、提供商条款」这套记录是为了证明**我们怎么造出这张图**；对用户送来的图，该证明的是**我们凭什么能用它**。强行要求提示词，只会教人编一份出来，记的还不如不记。

因此目录条目的 `origin` 现在有两种取值，校验按来源分叉：

### `project-ai-generated`（现有 39 张在架 + 52 张归档）

维持原全套要求，一项不减：`generation.tool==='image_gen'`、`review.status==='reviewed'`、`content/image-prompts` 里的真实提示词、每张参考图的来源/用途/授权与哈希、`commercialUse.basis==='provider-output-terms'` 及条款链接。

### `user-provided`（新增）

只要四项，记录在 `content/image-provenance/<id>.json`：

| 字段 | 要求 |
| --- | --- |
| `source.description` | 这张图从哪来、是什么 |
| `rights.basis` + `rights.statement` | 使用依据（如 `user-owned`）与提供者的授权原话 |
| `width` / `height` / `sha256` | 与 `public/puzzles/<id>.png` 实物一致 |
| `review.status==='reviewed'` | 有人真的看过原图，记录审核人与结论 |

**不需要**提示词、**不需要** `generation.tool`、**不需要**参考图哈希链、**不需要**提供商条款链接。

反过来，`user-provided` 条目**一旦带上 `generation` 字段就会被构建拒绝**——不允许拿用户提供的图伪造一份 AI 生成记录。`user-provided` 与 `project-ai-generated` 也必须与实际记录文件的 `origin` 一致，改一边不改另一边会直接报错。

### 两种来源共同强制、任何情况下不放宽的三条

1. **PNG 原件**：`public/puzzles/<id>.png` 必须是真正的 PNG（魔数 `89504e470d0a1a0a`），尺寸与 SHA-256 与记录完全一致。图片由用户提供，但原件本身照样核对——衍生图是从它算出来的。
2. **衍生交付记录**：`play`／`thumbnail`／`optimized`（以及有 `standardSrc` 时的 `standard`／`compact`）必须有完整记录并通过哈希、尺寸、体积、编码校验。用户提供的图**不是**免检通道。
3. **目录闭合**：`public/puzzles` 里每个文件都必须在目录中登记。这条是最实用的一道闸——它挡住的是「把图直接扔进目录就算上线」这种做法，两种来源一视同仁。

### 判定收口

来源判定集中在 `scripts/image-origin.mjs`（`PLAYABLE_ORIGINS`／`isPlayableOrigin`／`isRetained`／`isPublishedPlayable`）。此前 `origin==='project-ai-generated'` 硬编码散落在构建校验、两个交付编码器、发布打包、搜索提交和图库运行时共 6 处，加一种来源要改 6 个文件且容易漏改一处导致「图能显示但不进发布包」。现在**只改这一个文件**。新增来源类型时请改这里，不要再往各脚本里写裸字符串。

### 对外表述

`user-provided` 的图在界面上必须能与「本站 AI 生成」区分开，不能笼统宣称全部图片都是本站生成的。新增时目录条目与溯源记录的 `origin` 必须一致。

## 商用依据与检查边界

2026-09-08 核对的 [OpenAI 服务使用条款](https://openai.com/policies/row-terms-of-use/)规定，在用户与 OpenAI 之间且适用法律允许的范围内，输出归用户所有；同时用户须确保内容不侵犯他人权利，输出也可能不唯一。该依据不等于对所有司法辖区的可版权性、独占权或不侵权作保证。企业或 API 使用还应适用相应服务协议。

每张新图按以下流程入库（`project-ai-generated` 路径）：

1. 为拼图编写独立场景提示词，不上传未获授权的参考图，不要求复制知名作品、角色或商标。
2. 保存实际生成结果和实际提示词，不用放大文件尺寸冒充原生高清。
3. 查看是否存在明显水印、签名、品牌标志、可辨认的受保护角色、异常形体和大面积重复纹理；有疑点的版本保持草稿，重新生成或另行核查。
4. 记录生成工具、时间、可获得的模型信息、来源、SHA-256、原生尺寸、裁切比例、检查结论和条款依据。
5. 更新统一目录并执行来源检查。构建接受已审核的项目生成图，以及带来源与授权记录的用户提供图；未登记文件不能进入可访问的 puzzles 目录。

`user-provided` 路径只需第 3 步的目视检查、第 4 步中的来源/授权/尺寸/哈希，以及第 5 步的登记与校验。

## 扩充方式

先按风景、动物、植物、街景、建筑、美食、幻想和艺术等主题建立系列，再分批生成与挑选。先完成小批次的质量验证，再扩至数百、上千张；不以重复配色或简单裁切冒充新图。

- 每个主题保留多种构图、色彩、难度和细节密度，排除过度相似的候选。
- 每张作品保留不可变 ID 和原图；缩略图、4:3 展示图、2:1 拼图裁切是该作品的不同版本。
- 搜索以后扩展到题材、颜色、风格和难度标签；大量图片时胶片只渲染附近的少量卡片，目录分页加载，避免一次加载所有原图。
- 当前继续使用本地目录。大量内容阶段再规划对象存储、缩略图缓存和图库后台，当前不接入云服务或付费批量 API。
- 5000 片应单独验收：100 列网格若希望每块约 80 个原生横向像素，需约 8000 像素宽的真实细节。当前生成工具的实际输出尺寸须逐张检测；若做超分辨率处理，需另记处理方法，不能保证恢复原本不存在的细节。

## 文件与校验

- content/puzzle-catalog.json：统一的图片目录，供单人、多人及 WebMCP 共用。`origin` 取 `project-ai-generated` 或 `user-provided`。
- content/image-prompts：项目生成图的实际提示词（用户提供的图不需要）。
- content/image-provenance：原件尺寸、哈希、来源、检查与商用条款依据；用户提供的图记来源与授权说明。
- public/puzzles：仅存放已登记的可发布图片。
- scripts/image-origin.mjs：来源判定的唯一出处，新增来源类型只改这里。
- scripts/check-image-library.mjs：构建前校验，亦可单独运行。

本次仅整理现有图库并生成替换图，不代表已经生成了庞大图库，也未启动无人值守或付费批量生成任务。
