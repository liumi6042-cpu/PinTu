# 网页端与手机端游戏逻辑去重计划（草案，待确认）

日期：2026-10-25
范围：网页后端 `puzzle-play-web-h5-revamp`（不动 `puzzle-play` 主树）与手机后端 `jigsaw-nook-taptap`（`server/h5-gateway.mjs` + `server/mobile-service.mjs`）。
前提：两端数据库保持分离，账号打通不在本计划内。

## 一、现在哪些东西重复了

| 层 | 网页端 | 手机端 | 现状 |
|---|---|---|---|
| 1. 规则核心 `lib/*.ts` | 原版 | 复制出来的分叉，打包成 `outputs/mobile/engine.mjs` | 104 个同名文件：75 个完全相同，29 个已漂移 |
| 2. 共享客户端调用的 `/api/mobile/*` 接口 | `lib/shared-client-api.ts` + `shared-*`（约 620 行，适配到网页的房间存储和养成） | `mobile-service.mjs` + collection / tasks / social / economy（约 1300 行，自有 SQLite） | 同一套接口写了两遍；网页端缺补给、分享、广告、隐私、收藏购买/合成/装备等，返回 501 |
| 3. 养成规则 | `managed-economy-model.mjs`（等级、任务、礼物、相册购买、装饰合成） | `mobile-economy.mjs` 等（等级、体力、完成奖励池） | 各写一套，数值是否一致没人对过；手机有体力和广告，网页没有 |
| 4. 运维脚本 `server/*.mjs` | 原版 | 复制 | 21 个同名：18 个相同，3 个漂移（`runtime.node.mjs`、nginx 配置、`public-room-cleanup.mjs`） |

漂移最大、最关键的几个文件（差异行数）：`room-client` 237、`room-store` 207、`room-engine` 194、`connection-glow` 138、`cursor-client` 124、`puzzle-table` 95、`puzzle-engine` 55、`room-cursors` 16。

注意：漂移不全是 bug。例如 `puzzle-engine` 里桌面尺寸（网页 `WORLD` + `SHARED_WORLD`，手机直接把 `WORLD` 扩成共享桌面）、手机房间多出的 `mobileInviteCode` / `mobileSettled` / `diagnostic` 字段，都是有意差异。

## 二、可选方案

**A. 抽一个共享规则包（推荐）**
把纯逻辑（不碰数据库、不碰 HTTP）抽成 `jigsaw-core`：房间规则、拼图生成与吸附、同步记录、光标、片数策略、图库、每日拼图、插画升级、养成数值表。两端各自保留自己的存储和接口层，只调用这个包。有意差异用参数表达，不再靠复制改。

**B. 手机端改成调网页后端（单后端）**
去掉 `mobile-service`，网关直接转发到网页的共享接口。重复最少，但等于合并数据库、迁移 TapTap 登录和广告逻辑，还牵涉未定的账号打通。风险最大，也和“数据库分离”冲突，不建议现在做。

**C. 只加一致性测试，不动代码**
同一组房间回放用例同时跑两端引擎，结果不一致就报警。成本最低，但重复还在，只是漂移能被发现。

建议：A 为主，C 的测试作为 A 的安全网先做。

## 三、风险

1. **老房间存档兼容**：桌面坐标、`scatterVersion`、存档字段一旦变了，已有房间的棋子会错位。核心合并必须保证存档格式不变，并用真实存档样本回放验证。
2. **有意差异被抹平**：合并时如果直接取一边，会悄悄改掉另一端的行为（桌面大小、邀请码、8 人上限提示等）。每个漂移点要先分类再合。
3. **手机发版**：`engine.mjs` 是打进发布包里冻结的，发布脚本还会断言它的变化。改核心意味着手机后端要重新打包发版，这一步会先在线程里等你确认。
4. **运行环境不同**：网页是 Next.js，手机是 Node 24 + `node:sqlite`。共享包必须是纯 TS/ESM，不能依赖任何一端的平台 API。
5. **两个独立仓库**：手机树是单独的 git 仓库且没有远端，共享包放哪、怎么同步需要定下来（见下方待定）。
