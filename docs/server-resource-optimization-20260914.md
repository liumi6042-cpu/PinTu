# 服务器资源优化，2026-09-14

用户要求优先降低服务器资源与下载负担，允许暂缓高清和高片数。当前工作为现有线上服务的小步更新，不清房、不迁移数据库、不在服务器生图或转码。

## 开关与兼容

- 新建游戏只提供 108 / 300 / 500 / 1000 四档，默认 300。存储的旧高片数偏好回落 300。图片自身清晰度限制继续叠加。
- 服务端的公共图库、自上传新建入口都执行上限。底层网格和旧房间动作不套用新建限制，保留 12/48/1500/2000/3000/4000/5000 等旧局的恢复和续玩。
- 保留全部 30 张在架图片和 43 张归档图的 ID、原件、坐标及旧哈希文件。高清升级队列保留，自动化 `automation` 状态已改为 `PAUSED`；以后由用户决定恢复。

## 下载与图片预算

原件、无损版本保留，本机离线新增有损 WebP 交付版本。普通图使用 quality 84，三张完整高清图使用 quality 88，effort 5、smartSubsample。程序单并发、32 MB 编码缓存，网站请求不执行编码。

| 场景 | 交付文件 | 字节/尺寸策略 |
| --- | --- | --- |
| 图库和大厅卡片 | 既有 thumbnail | 最长 480 像素，不下载全部正图 |
| 新建 108–1000 片 | optimized；HD 优先 compact | 1774×887，实测约 0.15–0.62 MB/张 |
| 既有高清高片数房间 | 完整 optimized | 保留 3144×1572 或 3147×1574，约 1.32–1.81 MB/张 |
| 旧客户端/回退 | 旧 play、standard、thumbnail | 地址及内容保留，不强制刷新 |

30 张在架画面各下载一次的普通开局交付合计从 **62,768,688** 降至 **10,656,282** 字节，减少 **83.02%**。这不是一次打开图库就下载 30 张正图。全部 73 张完整优化资源加 3 张 compact 共新增 **32,632,336** 字节；为兼容旧客户端保留旧文件，因此磁盘不会同步下降 83%。跨版本相同哈希文件用硬链接复用，服务器仅保留当前版与一个回退版。

预算：完整 optimized ≤2 MiB，compact ≤700 KiB。构建校验实际静态 VP8 编码、尺寸、字节、SHA、源文件/input 哈希，来源记录明确 `lossless:false`，不是插值放大，也不宣称压缩增加细节。六张样本检查了原尺寸中心和前景裁切；q84 有轻微微纹理损失，高清 q88 对细节更稳。山湖与雪夜小镇的对比由主代理再次检查。

压缩减少网络传输，不会按相同比例减少同尺寸图片解码后的浏览器内存。单张 3147×1574 的 RGBA 像素缓冲约 18.9 MiB；1774×887 约 6.0 MiB，尚不含 Canvas 副本。暂停新高片数另行减少散片、状态序列化及多人同步的后续压力。

所有派生图使用内容哈希 URL，nginx 直接提供并设置 public/max-age=31536000/immutable；公开静态 WebP 可由已有 CDN 缓存。账号、API、私图不使用这个规则。不同 CDN 节点的首次 MISS 不能据此判断缓存失效，验证须记录具体响应。

## 请求与服务开销

- CursorClient 页面隐藏后不再循环 GET；发送一次空位置清除队友视图，处理在途位置，再休眠。可见后立即恢复，429/503 继续遵守 Retry-After。聊天原本已有后台停止逻辑，未提高其轮询频率。
- 公共大厅按稳定的底层 DB 对象共享单槽缓存。查询开始算起最长 1 秒、最多 24 张卡，并发合并，返回深复制。失败不缓存，切换 DB 后迟到查询不能覆盖新槽。个人/私人/管理查询保持独立，serverTime 每次生成，HTTP no-store。
- 保留房间授权、抢块、落片、存储与版本协议；没有把敏感响应放入公共缓存，也没有改写旧房间 JSON。新局上限会逐步降低压力，已有高片数房间仍有原来的计算需求。

优化前低负载采样：拼图 unit MemoryCurrent 59,469,824 字节，整机约 3,915 MB 内存、可用 2,296 MB；项目目录 292,499,456 字节。没有发现当时内存紧张，但这不是高峰容量承诺，没有对生产进行压力测试。10 MB 原图主要增加带宽和首开等待，不代表每位玩家都占用服务器 10 MB 常驻内存。
